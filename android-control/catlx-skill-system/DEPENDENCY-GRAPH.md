# CATLX Skill System — Dependency & Relationship Graph

> This graph corresponds to the **actual generated files** in `skills/`. Machine-readable form:
> `metadata/dependency-graph.json` (20 nodes, generated by `scripts/gen_graph.py`). Edge kinds:
> `depends_on` (acyclic prerequisites) and `delegates_to` (runtime routing, bounded/guarded).

## Two-layer model (why the graph is a DAG + guarded peers)

The system deliberately separates two relationship kinds so there are **no problematic cycles**:

- **`depends_on`** — *foundational prerequisite* knowledge/subsystem that must be understood before this
  skill. This is a **strict directed acyclic graph** (36 edges, **no cycles** — verified). It represents a
  bootstrap/learning order, not an execution loop.
- **`delegates_to`** — *runtime capability routing* used for automatic skill-to-skill invocation. These are
  **peer** collaborations (104 edges) and may form bounded clusters. They are **guarded at runtime** by the
  active-skill-chain check and a recursion-depth limit (see the root skill's delegation protocol). Peers are
  not prerequisites; a skill that `delegates_to` X does not *load* X as a prerequisite.

Consequence: there is no `A→B→A` prerequisite loop. Peer relationships that appear "mutual" in the source
(memory↔AI-provider, security↔recovery, electron-shell↔telemetry, desktop↔screen, docker↔portability) are
modeled **once** as `depends_on` in one direction and as `delegates_to` for the return path.

## Nodes

19 skill nodes: `catlx` (root) + `catlx-orchestrator` (Universal Mode) + 17 subsystem skills.
Canonical-knowledge nodes live under `knowledge/` (concepts, rules, references). Supporting nodes under
`workflows/`, `examples/`, `templates/`, `metadata/`.
Plus 1 integration node: `antigravity-last-resort` (terminal escalation bridge; depends_on catlx-ai-provider + catlx-capability-routing).

> **Orchestrator edges:** `catlx-orchestrator` has **`delegates_to`** edges to all 17 subsystem skills (it is
> an automatic router, not a prerequisite of anything). It has **no `depends_on`** edges, so it never creates
> a prerequisite cycle.

## Reference edges (read-only, canonical knowledge)

Every skill references one or more files in `knowledge/` (the single source of truth). These are **read-only**
and never a bootstrap prerequisite loop. They are listed per-skill as `references` in `INDEX.md` and in each
SKILL.md body.

## Cycle-safety & recursion control

- **`depends_on`:** verified acyclic (35 edges, DFS cycle check = **False**).
- **`delegates_to`:** contains **bounded** peer clusters, e.g. `catlx-ai-provider → catlx-security → catlx-telemetry → catlx-ai-provider`. These are not true infinite loops because:
  1. The runtime maintains an **active-skill chain** and **reuses the in-progress result** of an already-active
     skill rather than re-invoking it (cycle protection).
  2. A **recursion-depth limit** is applied to delegation.
  3. Each delegation is task-specific and minimal-context, so the chain unwinds as soon as the subtask completes.
- The three clusters identified in the source are modeled as **peer** (not prerequisite) relationships and are
  documented in each affected skill's "Delegation" section.

## Consistency with generated files

- Node set = the 19 directories in `skills/*` (matches `metadata/skills-registry.json`).
- `depends_on` = the `metadata.depends-on` field of each SKILL.md.
- `delegates_to` = the delegation targets in each SKILL.md body + `INDEX.md`.
- Generated programmatically; re-run `python scripts/build_registry.py && python scripts/gen_graph.py` after any
  change to keep it in sync.
